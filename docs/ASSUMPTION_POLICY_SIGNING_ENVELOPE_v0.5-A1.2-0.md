# Assumption Policy Signing Envelope v0.5-A1.2-0

**Status:** Contract correction (PR #51)
**Date:** 2026-08-03
**Scope:** Non-circular signing-envelope contracts and conformance tests

## 1. Lineage

### commit/2 and entry/2 — historical, parseable, not activatable

The V2 contracts (`assumption-authority-policy-commit/2`,
`assumption-policy-activation-proof/1`, `assumption-policy-ledger-entry/2`,
`assumption-policy-ledger/2`) froze the first executable shape of the
assumption policy activation envelope.

They included a self-referential signing dependency:
`signature_set_digest` is a commit field, and signatures target
`commit_receipt_digest`. Since the commit digest incorporates the
signature-set digest, and the signature records contribute to the
signature-set digest, the V2 envelope contains signatures over a digest that
contains the digest of those signatures. This creates a circular dependency
with no fixed point.

**No production data used the defective executable format.** The V2 contracts
were frozen but never activated by an executable preparer. The defect was
discovered while implementing executable D3.2-A1.2 preparation (PR #50, which
remains draft and must not merge until corrected against this envelope).

The V2 contracts remain independently parseable. The executable preparer
rejects them with `ASSUMPTION_POLICY_COMMIT_VERSION_NOT_ACTIVATABLE`. V2
entries cannot appear in a V3 ledger; the V3 ledger enforces exact
`AssumptionPolicyLedgerEntryV3` type at runtime (not only via type annotations)
and rejects foreign or V2 entries with
`ASSUMPTION_POLICY_LEDGER_ENTRY_VERSION_NOT_ACTIVATABLE`.

### signing-payload/1 + commit/3 + proof/2 + entry/3 — executable, non-circular

The V3 envelope separates the pre-signing payload from the post-signature
activation commitment:

```text
policy-generation commitments
  -> signing payload (assumption-policy-signing-payload/1)
  -> signing_payload_digest
  -> signatures target signing_payload_digest (NOT commit_receipt_digest)
  -> signature set
  -> signature_set_digest
  -> commit/3 binds (signing_payload_digest, signature_set_digest)
  -> commit_receipt_digest
```

The signing payload excludes all signature-derived fields
(`signature_set_digest`, signature bytes, activation proof, ledger-entry
digest, resulting ledger root). Signers sign a payload that does not
transitively depend on their signatures. There is no cycle.

The exact signed target is `signing_payload_digest`, validated by
`require_policy_signature_target()` with exact case-sensitive equality. Any
different target (policy digest, commit receipt, another payload, any other
digest) raises `ASSUMPTION_POLICY_SIGNATURE_TARGET_MISMATCH`.

## 4. Authority-root binding

`AssumptionPolicySigningPayload.build()` requires:

```text
approval_policy.authority_root_digest = policy.authority_root_digest
signature_profile.key_authority_root_digest = policy.authority_root_digest
```

Entry/3 repeats both checks as defense in depth.

## 5. Claim boundary

The deterministic conformance vector is explicitly non-production. It makes no
cryptographic claim. It commits to `algorithm`, `verification_profile`,
`public_key_bytes`, and `signed_digest`; changing only `signed_digest` changes
the generated bytes. A real cryptographic backend binds the signature to the
signed digest natively.

This envelope does not establish production cryptographic key validity,
external truth, model generalization, or production safety.
